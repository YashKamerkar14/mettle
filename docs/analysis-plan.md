# Analysis plan (pre-registered)

**Status: FROZEN on 2026-10-12**, before any main-set output existed. Code and data are pinned by the git tag `analysis-plan-v1-frozen`; model files are pinned by the SHA-256 hashes in `eval/freeze/manifest.json`. From here on this file is not edited. Any change goes in "Deviations" at the bottom, dated, with the reason.

Before freezing, the plan was reviewed adversarially by an independent review agent. Its must-fix items are all addressed below.

## Questions

1. **Compression trade-off.** On a fixed question set, how many points of accuracy does the 4-bit build (q4f16_1) lose relative to full precision (q0f16), and how much faster is it?
2. **Cross-device consistency.** For a fixed build, what share of visitor submissions reproduce the reference outputs exactly, and where they do not, at which token does output first diverge?

## Fixed settings

- Model: SmolLM2-360M-Instruct via WebLLM 0.2.86, builds q4f16_1, q4f32_1, q0f16, q0f32. Weight manifests and compiled libraries are pinned by hash (`eval/freeze/manifest.json`). Every run records the hashes it actually fetched (`launches.jsonl`). A mismatch is a deviation.
- Code path: `answerQuestion` in `web/src/quality/runQuestions.ts`. It is used by the offline runner (`eval/reference.mjs`) and by the site.
- Decoding: greedy. Each question is a single user message from an empty conversation (`resetChat`), `max_tokens` 16, top-2 log-probs recorded per token. Greedy is implemented as temperature 1 with `top_p` 1e-5, which leaves only the argmax token in the nucleus. Temperature 0 cannot be used: WebLLM clamps it to 1e-6, which makes every log-prob margin infinite. On the 48 pilot items, both builds produced token-for-token identical outputs under both settings.
- Reference device: the author's RTX 4080 Laptop GPU, Chrome, `--force_high_performance_gpu`.

## Question set

`eval/questions/questions.v1.jsonl` (SHA-256 `95ded352…38be8`), generated by `eval/questions/build.py` (seed 20261012). 500 items, 100 per category:

| Category | What it tests | Scorer | Chance |
| --- | --- | --- | --- |
| arithmetic | two-digit addition (36) and subtraction (64) | number | ~0 |
| compare | "which is larger / smaller" of two two-digit numbers | number | 50% |
| capital | capital city of a country; disputed or changing capitals excluded | phrase | ~0 |
| antonym | one-word opposite; several accepted answers | phrase | ~0 |
| sentiment | short templated review; 50 positive, 25 negative, 25 negated-positive | label | 50% |

**Answer-key policy** (in `eval/questions/data.py`, applied without looking at any main-set output):
- Capitals: any official name in use since 2015, plus common English spellings.
- Antonyms: direct antonyms of the most common sense of the word, plus common near-synonyms of those antonyms.

**Scope.** The items are templated and narrow. Results describe this set, not general model quality.

## Scoring (`eval/analysis/scoring.py`)

Only the first non-empty line of the output is scored.

- **Answer correct (primary).**
  - Phrase and number items: split the line into candidate segments: the whole line, the text before the first " is ", the text after the last " is ", and the text after the last "=" or ":". The answer is correct if any segment, normalised, *exactly* equals an accepted answer. This accepts "Reykjavik", "The capital of Iceland is Reykjavik.", "Reykjavik is the capital of Iceland.", "61 + 34 = 95" and "Answer: 95". It does not accept a sentence that only mentions the answer.
  - Label items: correct only if exactly one label is mentioned without a preceding "not", and that label is the key.
- **Followed format (co-headline).** The whole first line, normalised, equals the answer. This measures whether the model obeyed "answer with only …".
- **Normalisation:** lowercase, strip accents, delete quotes and apostrophes, turn markdown, hyphens and other punctuation into spaces. Numbers must normalise to a single integer.

## Primary endpoint

**Single primary endpoint:** the paired difference in "answer correct" accuracy, q0f16 − q4f16_1, over all 500 items equally weighted, using run 1 of each build.

- Test: exact two-sided McNemar test, α = 0.05.
- Estimate: paired bootstrap, 10,000 resamples over items, seed 0. Report the 95% and 90% CIs.
- **Equivalence margin ±5 points** (TOST via the 90% CI). The reading is pre-specified:
  - **loss:** 95% CI entirely above 0.
  - **gain:** 95% CI entirely below 0.
  - **equivalent:** 90% CI inside (−5, +5) and not significant.
  - **inconclusive:** anything else.
  - A significant loss whose 90% CI also lies within ±5 is reported as "loss, but within the equivalence margin".
- Expected precision, from pilot discordance: 95% CI half-width about ±4.5–5.5 points. The minimum effect detectable with 80% power is about 6–8 points.
- **Co-headline rule:** every headline sentence states both the answer-correct and the followed-format difference. One is never quoted without the other.

## Secondary and exploratory analyses

| Analysis | Method | Status |
| --- | --- | --- |
| Followed-format difference, q0f16 − q4f16_1 | paired bootstrap 95% CI, exact McNemar | secondary (co-headline) |
| Per-build accuracy, both scores | Wilson 95% CI | descriptive |
| Per-category difference | paired bootstrap 95% CI (not multiplicity-adjusted), McNemar p Holm-adjusted across 5 categories | exploratory; underpowered below about 20 points per category |
| Binary categories (compare, sentiment) | also reported as accuracy above the 50% chance level | descriptive |
| f32 pair, q0f32 − q4f32_1 | same as the primary endpoint | secondary robustness check. If it disagrees with the f16 reading, both are reported and no single "4-bit cost" is claimed |
| Truncation | share of outputs that stopped at `max_tokens` 16, per build | descriptive |
| Truncation sensitivity | truncated items re-run with `max_tokens` 64 (greedy, so the first 16 tokens are unchanged), re-scored, difference recomputed | secondary |
| Output agreement between builds | identical-output rate; first divergent token; q0f16's top-1 vs top-2 log-prob margin at that token vs all tokens | descriptive |

## Scorer validity audit (blinded)

The scoring rule was designed after inspecting pilot outputs, including the observation that q4f16_1 answers in full sentences far more often. To check that the rule does not favour one build:

1. Sample every item where the two f16 builds disagree on "answer correct", plus a random 50 items per build (seed 1).
2. Show each (question, accepted answers, output) to an independent adjudicator in shuffled order, **without the build label or the scorer's verdict**. The adjudicator is a separate LLM review agent. The author then checks 40 random adjudications and reports the agreement rate.
3. Report the scorer's false-positive and false-negative rates per build, and the primary difference recomputed with adjudicated labels on the audited items.
4. If the adjudicated difference falls outside the primary 95% CI, adjudicated labels become primary. This is reported as such, not as a deviation.

## Same-device determinism

- Each build runs in 3 independent browser launches on the reference device (runs 1–3; run 3 uses a fresh profile, so weights and shaders are fetched and compiled anew). A 4th run goes through the public site in a headed browser.
- Report the within-device mismatch rate per build. If it is above 0, items that mismatch on the reference device are excluded from cross-device attribution, and the cross-device rate is reported alongside the within-device rate.

## Speed (question 1, second half)

- Reference device only. **10 sessions**: each a fresh browser launch, laptop plugged in, fixed power mode, 5 minutes idle before starting, weights cached.
- Within each session, ABBA order (q4f16_1, q0f16, q0f16, q4f16_1). Each block is the site's harness: 1 warm-up and 3 timed generations of 128 tokens from the fixed 458-token prompt.
- Per-session statistic: median 4-bit decode tok/s ÷ median full-precision decode tok/s, measured on the main thread. WebLLM's internal figure is a cross-check.
- Report the geometric mean of the 10 ratios with a t-interval on log ratios. Prefill speed ratio is secondary, computed the same way.
- The integrated GPU (Radeon 610M) is reported the same way as a second device, if run. No claim about devices in general.

## Cross-device consistency (question 2)

- **Subset.** Rule fixed now and applied mechanically after the main run: for each category, the 5 items whose q0f16 run-1 output has the smallest minimum top-1 vs top-2 log-prob margin, ties broken by id. That gives 25 items, written by `analyze.py --make-subset`. Its SHA-256 is recorded, and the same file ships with the site.
- **Reference.** The reference device's run-1 outputs for the same build. f16 devices are compared against f16 references, f32 against f32.
- **Match.** Identical generated token sequence and identical finish reason, on all 25 items. Also reported: the per-item match rate.
- **Unit.** One submission per anonymous client id per build. The first is kept and repeats are discarded. Adapter info is too coarse to identify a physical device, so the claim is "share of submissions", not "share of devices".
- **Interval.** Wilson 95% CI on the match share.
- **Stopping rule.** Collection for this analysis ends at 150 valid submissions per build or on 2027-01-31, whichever comes first. Match rates are not examined before that.
- **Exclusions.** Incomplete runs, engine errors, or a runtime version, question-set hash or model-artifact hash that differs from the reference. **No exclusion for failing the instant-score CPU check.** Those devices are exactly the numerically unusual ones; their submissions are reported separately rather than dropped.
- **Reporting.** By GPU vendor and architecture as reported by the browser. This is a self-selected convenience sample, and no population claim is made.
- **Drift check.** At the start and end of collection, the reference device runs the subset through the public site. If its own outputs change, collection stops and a dated deviation is added.

## Crowd speed data

Speed results from visitors are descriptive only (distributions by device class). Exclusions: any non-positive timing, decode speed above 2,000 tok/s, or a mismatched runtime or prompt version.

## Null results

All outcomes are reported, including "equivalent", "inconclusive", or every device matching.

## Calibration and other decisions made after the pilot

Rule: on a separate 48-item pilot (`eval/questions/pilot.v1.jsonl`, 8 per category, disjoint from the main set), drop any category where q0f16 scores below 25% or above 95% ("answer correct").

Pilot run on 2026-10-12 (`eval/results/pilot/`), scored with the scorer at that time:

| --- | --- | --- |
| antonym | 87.5% | keep |
| arithmetic | 87.5% | keep |
| capital | 62.5% | keep |
| compare | 62.5% | keep |
| sentiment | 75.0% | keep |
| sequence | 0.0% | **dropped** |

Re-scoring the pilot with the frozen scorer (`eval/results/pilot-topp/`) gives the same decisions.

**For transparency, these were all written or changed after seeing pilot outputs:**
- the scoring rule;
- the choice to report both scores side by side, with "answer correct" as primary;
- the move from temperature 0 to the top-p greedy setting;
- 14 accepted-answer additions under the key policy.

The key policy itself was applied without consulting outputs. Two additions suggested by pilot outputs ("unfreeze", "recent") were rejected for that reason. The calibration thresholds were set before the pilot.

## Deviations

**2026-10-12, speed protocol.** The plan says "10 sessions" with AC power and 5 idle minutes, but doesn't say what happens to a session that breaks those conditions. Four sessions broke them and were excluded, by condition and not by their values. Sessions 3–4: the laptop was unplugged (Windows power event). Sessions 5–6: the author's tooling ran during their idle windows. All four were replaced with new sessions until 10 valid ones existed (sessions 1–2 and 7–14). The excluded sessions stay in `eval/results/speed-v1/sessions.jsonl`, with reasons in `excluded.json`. The runner now checks AC power before and after every session.
